1. Bloqueo de permisos en el asistente de desarrollo

Sintoma: cada comando de terminal (git, Maven) pedia aprobacion manual, incluso despues de haber autorizado comandos similares repetidas veces durante la misma sesion.
Causa: el sistema de permisos evalua el comando completo como texto. Pequenas variaciones invalidaban las reglas ya autorizadas:
  • Anteponer cd "ruta" && antes de un comando de git rompia la coincidencia con la regla.
  • Comandos con tuberias (| tail -60, | tail -150) se evaluaban como un comando distinto cada vez que cambiaba el numero de lineas.
  • Subcomandos especificos de git (git checkout) no estaban cubiertos por una regla generica que solo autorizaba status, diff, add, commit, push.
Resolucion: se activo "defaultMode": "bypassPermissions" tanto en la configuracion del proyecto (.claude/settings.local.json) como en la configuracion global del usuario (~/.claude/settings.json), eliminando la necesidad de autorizar cada comando individualmente. Resuelto.

2. Credenciales reales de conexion a la base de datos H2

Sintoma: no se conocia el usuario y contrasena reales que usa la aplicacion para conectarse a su base de datos H2, necesarios para poder abrirla con una herramienta externa. El supuesto habitual (usuario sa, sin contrasena) resulto incorrecto.
Causa: application.properties nunca define explicitamente spring.datasource.username ni spring.datasource.password. Spring Boot arma la conexion con los valores por defecto de esas propiedades, que son cadena vacia en ambos casos, no sa.
Diagnostico: se agrego temporalmente un metodo @PostConstruct a un bean real de la aplicacion (ya conectado a la base) que imprimia conn.getMetaData().getUserName() directo a consola. El resultado fue una cadena vacia. Se confirmo conectando por JDBC de forma directa (fuera de la aplicacion) con usuario y contrasena vacios, logrando la conexion exitosamente.
Resolucion: se documento el dato real (usuario y contrasena vacios) en el script abrir-base-datos-h2.bat, y se retiro todo el codigo de diagnostico temporal una vez confirmado el dato. Se confirmo explicitamente que no se debe forzar spring.datasource.username=sa en application.properties, ya que eso rompe la conexion real de la aplicacion (probado y revertido durante esta misma investigacion). Resuelto.

3. Componentes de Vaadin sin renderizar en pantallas nuevas

Sintoma: al crear una pantalla nueva (por ejemplo, el registro de tareas de Barril y Tornillo o el catalogo de Personal de Mantenimiento), algunos componentes de la interfaz (Grid, ComboBox, NumberField, DateTimePicker) no aparecian en absoluto en la primera visita a esa pantalla. El resto del formulario (campos de texto simples, botones) se veia con normalidad. Visitar otra pantalla y volver a veces "arreglaba" el problema temporalmente, pero de forma inconsistente.
Diagnostico: se descarto que fuera un error de programacion revisando, con JavaScript ejecutado directo en el navegador, si el elemento HTML personalizado de cada componente llegaba a registrarse: 
customElements.get('vaadin-grid')  // devolvia false
customElements.get('vaadin-combo-box')  // a veces true, a veces false
Esto confirmo que el servidor si enviaba el componente (existia en el HTML de la pagina), pero el navegador nunca terminaba de "activarlo" como elemento funcional. Se comparo contra pantallas antiguas del sistema (por ejemplo, Configuracion de Alarmas), que siempre funcionaban bien incluso en una carga totalmente nueva.

Se construyeron dos pantallas de prueba minimas (solo un Grid con datos de ejemplo, sin ningun otro campo) para descartar que el problema fuera la combinacion de campos de una pantalla especifica. El problema se reprodujo igual en esas pantallas minimas, confirmando que no dependia del contenido de cada vista sino de que la ruta fuera nueva.
Causa raiz (dos factores combinados):
  1. Paquete de JavaScript desactualizado: el archivo src/main/bundles/prod.bundle (el paquete de codigo de interfaz pre-generado que usa la aplicacion en modo produccion) no reflejaba las rutas mas nuevas del proyecto. Intentos de "actualizarlo" con los comandos normales de Maven no generaban cambios porque el sistema de build de Vaadin asumia, de forma incorrecta, que el paquete existente seguia siendo valido.
  2. Carga diferida por defecto de Vaadin: Vaadin solo incluye en el paquete de carga inmediata (siempre presente) las rutas "" (raiz) y /login. Todas las demas rutas cargan sus componentes bajo demanda, en modulos separados que el navegador pide la primera vez que se necesitan. En una ruta realmente nueva, con un paquete recien reconstruido y sin nada en la cache del navegador, esa descarga bajo demanda de varios modulos en simultaneo puede perder una carrera de tiempos, dejando el componente sin registrar. Rutas antiguas no mostraban el problema porque el navegador ya tenia esos modulos guardados en cache de usos anteriores.
Resolucion (dos pasos):
  1. Se elimino manualmente el archivo src/main/bundles/prod.bundle y se dejo que Maven lo reconstruyera completamente desde cero (no una actualizacion incremental), mediante el goal build-frontend del vaadin-maven-plugin ya configurado en el proyecto. Esto resolvio el caso en que una ruta nueva nunca funcionaba, sin importar cuantas veces se visitara.
  2. Para eliminar la carrera de tiempos residual (que persistia de forma ocasional incluso con el paquete actualizado), se agregaron anotaciones @Uses sobre la clase principal de la aplicacion (Application.java, que implementa AppShellConfigurator): 
    @Uses(Grid.class)
@Uses(ComboBox.class)
@Uses(NumberField.class)
@Uses(DateTimePicker.class)
    Esta anotacion le indica a Vaadin que incluya esos componentes en el paquete de carga inmediata (el mismo que ya usan "" y /login) en lugar de en un modulo bajo demanda, eliminando la necesidad de una descarga adicional -y su riesgo de carrera de tiempos- en cualquier ruta nueva.
Se confirmo la resolucion con multiples pruebas consecutivas, incluyendo reinicios completos de la aplicacion, verificando en cada caso que los cuatro componentes se registraran correctamente en la primera visita. Resuelto.

Referencias externas consultadas

  • Documentacion y foros de Vaadin sobre el comportamiento de carga diferida (lazy loading) por defecto en modo produccion, confirmando que solo las rutas raiz y de login se empaquetan de forma inmediata por defecto.
  • vaadin/vaadin-grid-flow issue #557 - "Grid components are not always rendered immediately" (reporte oficial de Vaadin sobre demoras de renderizado en el componente Grid).
  • Vaadin - Troubleshooting de despliegue en produccion (documentacion oficial sobre configuracion de productionMode y archivos de build).

4. Estados sin color (badges) en las grillas

Sintoma: la columna Estado del reporte de Barril y Tornillo se veia como texto plano, sin el fondo verde, amarillo o rojo esperado.
Causa: el tema del proyecto es Aura (@StyleSheet(Aura.STYLESHEET)), no Lumo. Los theme variants de Lumo ("badge", "success", "error") no se pintan bajo Aura.
Resolucion: cada estado es un Span con estilo inline (background-color, color, padding, border-radius), que se ve igual sin depender del tema. Paleta: verde #d4edda/#155724, amarillo #fff3cd/#856404, rojo #f8d7da/#721c24, gris #e2e3e5/#383d41. Resuelto.

5. Campo Cantidad invisible en Stock

Sintoma: el formulario de Stock de Barril y Tornillo no mostraba el campo Cantidad.
Causa: IntegerField no estaba en la lista de @Uses. Es la misma familia de la falla 3: un componente que carga por demanda en una ruta con bundle recien generado puede no registrarse.
Resolucion: se agrego @Uses(IntegerField.class) en Application.java y se regenero prod.bundle. Regla preventiva: cada componente Vaadin nuevo en una vista lleva su @Uses y se regenera el bundle en el mismo cambio. Resuelto.

6. Horometro de una tarea con error de unas 8 horas

Sintoma: el horometro sugerido para una tarea registrada a las 09:54 mostraba 3257.0 h; el valor exacto a esa hora era 3249.1 h.
Causa: el metodo anterior sumaba las filas diarias hasta el dia de la tarea inclusive, o sea el dia completo. El error de cada registro es lo que la linea trabajo despues de la hora de la tarea ese mismo dia; no se acumula con el tiempo porque los dias anteriores son exactos y cada calculo parte de cero. Ademas, las horas actuales omitian el tramo encendido en curso.
Resolucion: un metodo nuevo suma exactamente los dias anteriores (una sola consulta agregada) y calcula desde los datos crudos solo el dia de la tarea, cortado en la hora exacta; las horas actuales usan el estado en vivo. Costo fijo por llamada, no crece con la antiguedad de la fecha. Los registros viejos no se recalculan solos: se borran y se vuelven a cargar. Resuelto.

7. Confusion de puerto 8080 / 8081 en las pruebas

Sintoma: el preview del asistente arrancaba en el 8081 mientras el usuario prueba en el 8080.
Causa: el 8080 lo ocupa la propia instancia del usuario (IntelliJ, con la base real). No es un rango reservado por Windows (la consulta de puertos excluidos salio vacia). Dos instancias no pueden compartir puerto.
Resolucion (flujo): compilar, commit y push a master; el usuario hace pull, recompila y reinicia su instancia en el 8080 y prueba ahi. No se levanta un preview en el 8081 salvo pedido expreso. Resuelto.

8. Login por automatizacion del navegador no ingresa texto

Sintoma: al escribir usuario y clave con el navegador integrado, los campos quedaban vacios y el ingreso fallaba aun con la clave correcta.
Causa: un clic simple no da foco al input interno del componente web de Vaadin.
Resolucion: usar doble clic para enfocar y verificar por JavaScript el valor de los campos antes de enviar. Resuelto.

9. Restaurar un commit viejo deja un arbol inconsistente

Sintoma: al volver a un commit anterior con git checkout <sha> -- . quedaban archivos que no existian en ese commit.
Causa: ese comando solo restaura archivos presentes en el commit, no borra los agregados despues.
Resolucion: para reflejar el arbol completo usar git checkout <sha> o crear una rama desde ese commit; para traer un arreglo puntual, git cherry-pick. Guardar antes el trabajo pendiente con git stash push -- <rutas>. Resuelto.
